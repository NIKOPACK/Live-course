# LiveCourse 功能说明与下一阶段实现目标

> 文档性质：下一阶段的产品功能规格与验收基线，不等同于当前版本功能清单。
>
> 产品基线：[LiveCourse 作品简介](./LiveCourse_作品简介.md)
>
> 目标用户：大中学生、语言学习者、职教培训者，以及保留课程控制权的教师。

## 1. 目标与成功标准

LiveCourse 要成为“会教书的老师”，而不只是回答问题的聊天机器人。下一阶段以完整的**教—学—评—调**闭环为交付目标：系统能够为一个具体学习者备课、主动授课、收集可信学习证据，并据此调整当前或后续教学。

完成下一阶段时，一名学习者应能在同一门课程中完成以下体验：

1. 用一句话或上传资料创建学习目标与课程计划；
2. 进入由 AI 教师主动组织的课堂，而非空白聊天页；
3. 在讲解中随时语音打断，得到回答后回到原教学节点；
4. 遇到需要准备、检索、板书或辅导的任务时，实时教师将任务派给助教 Agent；
5. 在检查点完成题目、任务或项目提交，看到依据明确的反馈；
6. 课堂根据已记录的证据决定继续、补讲、降低难度、增加练习或进入下一课时。

以下不构成成功：只生成一组页面、只进行一次问答、只输出模型判断但不保存证据，或把教学调整隐藏在无法解释的提示词里。

## 2. 范围与优先级

| 优先级 | 目标 | 结果 |
| --- | --- | --- |
| P0 | 单课程的闭环课堂 | 可演示并可恢复的“备课 → 授课 → 检查 → 调整”最小闭环。 |
| P0 | 实时教师与助教协作 | 全双工教师可派发任务，助教执行并将结果可见、可审计地回传。 |
| P0 | 证据驱动调整 | 每次学习调整都能追溯到检查点、提交、评分或教师复核。 |
| P1 | 多课时课程规划 | 用学习证据重排后续课时、插入补课或巩固任务。 |
| P1 | PBL 与学科 Skill | 将 PBL v2 与可复用的学科能力接入同一课程闭环。 |
| P2 | 长期学情与课堂感知 | BKT/FSRS、跨设备档案和低风险课堂感知。 |

P0 是下一步实现门槛；P1、P2 不得阻塞 P0 的可用交付。

## 3. 目标用户与关键场景

| 用户 | 关键问题 | 目标体验 |
| --- | --- | --- |
| 自主学习者 | 不知道从哪里开始，遇到卡点也无法获得连续指导 | 系统先给出学习路线，按当前掌握程度讲解和练习。 |
| 教师 | 备课与个别辅导成本高，AI 内容又不可控 | 教师以资料、目标、规则和审阅权控制课堂，AI 承担备课与课堂执行。 |
| 语言学习者 | 需要实时口语互动、纠错和持续复习 | 能与实时教师对话，在情境任务中获得反馈并记录薄弱点。 |
| 职教培训者 | 操作步骤、安全要求和任务完成情况难以在普通问答中管理 | 以任务、检查和项目产出推进学习，明确完成条件与补救路径。 |

## 4. 端到端目标流程

```text
学习需求 / 课程资料 / 学习者档案
                ↓
课程规划 Agent：目标、前置关系、课时、检查点与证据规则
                ↓
备课 Agent：多场景课堂与课堂动作
                ↓
实时教师：主动讲解、语音互动、节点恢复、派发任务
                ↓
助教 Agent：完成受派任务并返回可审计结果
                ↓
检查点 / 测验 / PBL 提交 / 教师复核
                ↓
证据台账 → 目标状态 → 教学调整 → 下一节点或下一课时
```

每个箭头都应有明确输入、输出、责任主体和持久化边界。模型可以生成内容和建议，但课程状态、证据状态、任务状态和推进决策必须由可验证的数据契约承载。

## 5. P0：课程创建与可执行教案

### 5.1 输入与学习者档案

用户可输入学习主题、目标、已有基础、可用时间和偏好，并可上传课件、笔记、文档或媒体材料。系统需要将这些输入组织为可复用的课程上下文，而不是仅拼接为一次模型提示。

**验收条件**

- 可以从自然语言需求和至少一种课程材料创建课程；
- 学习者的基础、语言和目标会影响课程难度、示例和表达；
- 每项外部资料保留来源、解析结果和可引用位置；
- 材料解析失败、模型不可用或资料不足时返回明确错误，不生成伪成功课程。

### 5.2 课程计划

课程规划的最小产物必须包含：

- 学习目标及其可判定规则；
- 知识点与前置关系；
- 一个或多个课时，每个课时包含教学节点；
- 每个目标至少一个检查点或等价证据来源；
- 复讲、练习、补课或推进的候选调整路径。

现有 `LessonPlan`、`LearningGoal` 与 `GoalRule` 是单课堂计划的基础。下一阶段需要把它们提升为可跨课时维护的课程计划，同时保持课堂级计划可独立加载与恢复。

**验收条件**

- 首次生成后，用户能在界面中查看目标、课时和每课检查点；
- 修改课程目标会标记受影响的后续课时，而不是静默沿用旧内容；
- 课程计划中的每个节点都可定位到具体场景、任务或检查点；
- 教师可确认、调整或拒绝计划后再开课。

### 5.3 课堂内容与编辑

一节课由幻灯片、测验、白板、互动和 PBL 场景组成。生成内容必须服务于课程计划，不能因为模型输出格式碰巧可渲染就跳过目标与检查点。

**验收条件**

- 生成场景能引用所属目标、节点和材料来源；
- 教师可以编辑文字、媒体、题目、动作与 Agent 角色配置；
- 编辑后会使相关生成物和教学计划失效或更新，避免出现内容已改但检查规则仍针对旧内容的双重事实；
- 课程可以保存、重新打开、导出与导入，且不丢失目标、场景和关联资源。

## 6. P0：主动课堂与多模态实时教师

### 6.1 主动授课

实时教师必须由当前课堂计划驱动：进入节点后介绍目标、讲解内容、安排互动、打开检查点，并在完成条件满足后推进。它不应把“下一步做什么”完全交给学习者提问。

课堂动作覆盖场景导航、元素高亮、指针、白板、来源展示、教师表情和语音状态。现有 `TeachingAction` 与课堂控制器应继续作为动作的唯一执行入口。

**验收条件**

- 开始课堂后，教师能在无文本输入时主动发起本节点教学；
- 每个教学动作带有课程、课时、节点、序列和幂等键；
- 刷新或断线恢复后，课堂回到最后一个已提交的稳定节点；
- 任何无法执行的动作都返回可见错误，不标记为已完成。

### 6.2 全双工语音与虚拟教师

学习者可以通过自然语音与教师打断式交流。系统需要将实时音频、教师形象、课堂动作和当前教学上下文保持一致。

**验收条件**

- 学习者说话时，可中断正在输出的教师语音；
- 教师先处理打断内容，再恢复到被中断的教学节点；
- VRM 教师形象与语音状态同步呈现讲解、思考、视线、表情和口型；
- 未配置实时供应商、浏览器拒绝麦克风或网络中断时，状态与错误对用户可见，普通课堂不受破坏；
- 不将原始音频、密钥或短期实时凭证写入课堂日志。

## 7. P0：实时教师派发助教任务

### 7.1 目标行为

当全双工实时教师判断当前工作不应由自己在语音回合中直接完成时，必须派发给当前课堂中的助教 Agent。典型任务包括：准备板书或例题、检索并整理课程材料、为不同基础给出解释草稿、生成练习初稿、检查学习者提交，或完成被教师明确委托的辅助工作。

实时教师负责教学节奏、任务委托与结果讲解；助教负责执行受限任务。助教不能绕过教师擅自推进课程、判定掌握、删除课堂内容或调用未授权工具。

### 7.2 任务契约

任务至少包含以下字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 全局唯一任务 ID。 |
| `courseId` / `lessonId` / `nodeId` / `sceneId` | 任务所属的课堂上下文。 |
| `delegatedBy` / `assigneeId` | 实时教师与被选助教。 |
| `kind` | 受控任务类型，例如 `prepare_explanation`、`prepare_board`、`research_source`、`draft_exercise`、`review_submission`。 |
| `instruction` | 教师发出的、可展示的任务说明。 |
| `input` | 任务所需的已授权课堂上下文和材料引用。 |
| `status` | `queued`、`running`、`succeeded`、`failed`、`cancelled`。 |
| `result` / `error` | 成功产物或明确失败原因。 |
| `createdAt` / `completedAt` / `idempotencyKey` | 时序、恢复与去重依据。 |

任务状态是课堂事件的一部分，必须持久化并可在恢复后重新显示。实时模型只可以请求创建任务；任务的路由、权限检查、状态变更和结果回写由应用控制。

### 7.3 派发与回传流程

```text
实时教师提出 delegate_assistant_task 工具调用
                 ↓
应用校验当前课堂、助教身份、任务类型和输入范围
                 ↓
创建任务事件并将任务交给助教执行器
                 ↓
助教流式执行受限工具 / 生成结果
                 ↓
写入 succeeded 或 failed 结果事件
                 ↓
实时教师获取结果，向学习者说明并决定下一教学动作
```

**验收条件**

- 实时教师可以在一轮语音对话中创建助教任务，并向学习者明确说明正在委托什么；
- 任务卡片展示助教、状态、输入摘要、结果或失败原因；
- 任务结果必须经过教师确认后才写入白板、场景或学习反馈；
- 同一 `idempotencyKey` 不得重复执行同一任务；
- 学习者打断、课堂切换或会话关闭时，应用按任务类型取消或保留任务，并将最终状态可见地记录；
- 任务失败时，实时教师收到结构化失败结果并向学习者说明，不得虚构“助教已完成”；
- 所有助教工具调用受 allowlist、输入 schema、配额和课堂上下文约束。

## 8. P0：检查、证据与教学调整

### 8.1 检查点与证据

每个关键目标应至少有一种可接受证据：客观题得分、量规评分、项目提交、教师复核或任务完成记录。学习者自述可以作为上下文，但不能单独证明掌握。

现有 `EvidenceRecord`、`GoalState` 和 `evidence-reducer` 是此模块基础。下一阶段要保证所有评分、复核与调整都通过同一证据边界，不允许聊天文本直接改写掌握状态。

**验收条件**

- 每条证据记录来源、评分方式、量规/规则版本、置信度和复核状态；
- 模型低置信度评分进入待复核，不能直接标记目标已掌握；
- 目标状态只由已接受证据投影得出，并可重新计算；
- 用户可以查看“为什么系统认为我需要支持或已经掌握”。

### 8.2 教学调整

教学调整是一个可审计决策，而不是散落在对话提示中的自然语言。它至少说明依据、目标、动作和预期结果。

| 调整动作 | 触发示例 |
| --- | --- |
| 继续推进 | 当前目标达到通过规则。 |
| 同类练习 | 理解存在但独立完成不足。 |
| 缩小范围提示 | 学习者在检查点卡住，需要第一层支架。 |
| 拆分讲解或示范 | 多次失败或错误集中在同一前置概念。 |
| 补课/重排后续课时 | 当前目标未达标，后续知识依赖它。 |
| 提高难度 | 连续独立、高质量完成。 |

**验收条件**

- 每次调整关联至少一条证据或教师显式指令；
- 调整生成新的 `TeachingAdjustment` 记录，并标记被替换或新增的节点；
- 应用能在课堂内立即执行安全的调整，在课程级安排中生成待教师确认的建议；
- 教师可以接受、修改或拒绝调整，决策结果同样被记录。

## 9. P1：多课时规划、PBL 与学科能力

### 9.1 多课时课程

P1 将单课堂闭环扩展为课程级连续学习。系统根据目标依赖、已接受证据、学习时间和教师策略调整后续课时，不重写已完成的学习历史。

**验收条件**

- 课程至少可包含多个课时，并展示每个课时的状态与依赖；
- 未达标目标能插入补课或巩固课，已掌握内容可缩减重复讲解；
- 课程级调整保留历史计划版本和差异；
- 学习者与教师能看到下一课安排及其依据。

### 9.2 PBL v2 融入课程闭环

PBL v2 的 planner、instructor、simulator 和 evaluator 是项目式学习的执行基础。下一阶段要让 PBL 结果成为课程证据的一部分，而非与普通课堂分离的孤岛。

**验收条件**

- PBL 微任务、提交、评价和熟练度信号可映射到课程目标；
- 项目评价结果进入统一证据台账；
- PBL Instructor 产生的推进与补救建议遵从课程级调整规则；
- 情境模拟中的角色行为不会直接篡改学习证据或课程计划。

### 9.3 学科 Skill

学科 Skill 是建立在统一课堂底座上的可插拔能力，不是绕开课堂状态的独立聊天机器人。首批优先覆盖代码执行、数学推导、语言口语与材料分析中的一种或两种。

**验收条件**

- Skill 声明输入、输出、工具权限、适用目标和证据格式；
- Skill 的结果可被场景、助教任务和检查点复用；
- 新增 Skill 不复制课程计划、证据或权限逻辑。

## 10. P2：长期学情与课堂感知

P2 只在 P0 的证据和调整闭环稳定后推进。

| 能力 | 目标 |
| --- | --- |
| BKT 掌握模型 | 在规则型目标状态之外维护可解释的掌握概率。 |
| FSRS 复习调度 | 基于遗忘与复习记录安排复习节点。 |
| 长期学习档案 | 跨课程保存已接受证据、常见错因、有效支架与偏好。 |
| 课堂感知 | 只采集完成教学所需的低风险信号，并让用户可见、可关闭。 |

所有 P2 能力必须遵循最小化数据原则：默认不保存原始视频；任何感知信号不得单独决定成绩或掌握状态；用户和教师必须能查看、纠正或关闭相关数据使用。

## 11. 关键领域不变量

以下规则是实现时不可破坏的边界：

1. 课程计划、课堂动作、证据、助教任务和调整各有唯一写入入口；
2. 模型输出只能作为建议或受控命令，不能直接修改持久化状态；
3. 所有可重试操作都要使用稳定 ID 与幂等键；
4. 任务和课堂恢复以已提交事件为准，不根据模型记忆推测；
5. 评分、掌握与调整必须能说明依据；
6. 实时教师和助教只拥有各自白名单内的工具权限；
7. 原始音视频、供应商密钥和敏感学习资料不得进入不必要的日志或提示上下文；
8. 单一失败不能被静默吞掉：界面、事件流和任务记录都必须有明确失败状态。

## 12. 非目标

下一阶段不以以下事项为交付目标：

- 面向第三方的开放平台或稳定公共 API；
- 多租户组织、完整账号体系和实时多人协作；
- 用通用模型自动替代教师对课程质量、事实与安全的审核；
- 保存原始摄像头画面或把注意力识别当作学习成绩；
- 在没有证据的情况下自动宣布掌握、跳过课程或调整难度；
- 为每个学科同时构建一套独立 Agent、状态和权限系统。

## 13. 分阶段验收

### 阶段 A：单课堂闭环

交付课程计划、可执行节点、主动课堂、检查点、证据台账和基于证据的节点级调整。用一个学习主题验证：学习者完成检查后，系统能说明并执行“继续”或“补救”中的一个选择。

### 阶段 B：实时教师与助教协作

交付 `delegate_assistant_task` 的工具、任务状态机、助教执行器、结果回传和课堂可视化。用一个语音场景验证：教师将“准备一个针对当前误解的例题”派给助教，助教返回草稿，教师确认后展示并继续授课。

### 阶段 C：课程级连续学习

交付多课时计划版本、课后调整建议和教师确认流程。用两个连续课时验证：第一课的证据会改变第二课的起始节点或练习安排。

### 阶段 D：PBL 与学科 Skill

让 PBL 的提交与评价进入统一证据链，并接入至少一个有明确契约的学科 Skill。

## 14. 与现有实现的关系

现有课程生成、四类场景、课堂播放引擎、实时语音、VRM 教师、证据台账、PBL v2、编辑器、浏览器/PostgreSQL 存储和 MP4 渲染是本规格的实现基础。下一步工作的重点不是再增加平行入口，而是把这些能力通过课程计划、助教任务和证据驱动调整连接为一条可恢复、可解释的主链路。
